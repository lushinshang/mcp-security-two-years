章節 1：開場：為什麼 MCP 安全很重要（00:00）

00:00 準備好了嗎？好的，太棒了。我們這就開始。嗨各位，我是 Den。我是 MCP 的主要維護者（lead maintainer）之一，今天要回顧 MCP 安全性這 2 年，天啊，這週來談安全性真是再適合不過了。我記得很早以前有一篇部落格文章讓我印象特別深刻，上面寫著「MCP 中的 S 代表安全性」。我稍微想了一下。心想，老天，我們在 MCP 安全性上肯定能做得更多，好讓人們別再寫出那種東西。

00:35 而如果我們回顧 MCP 這不到 2 年的時間，我們實際上做了相當多的努力，我很期待今天能和大家分享。

章節 2：三大支柱：規格、SDK、最佳實務（00:40）

00:43 那麼，MCP 安全性本身基本上仰賴三大支柱，如果你想這麼稱呼的話。或者說我稱它們為支柱。隨你怎麼稱呼，但基本上首先是協定規格。也就是我們在做的東西。也就是大家看到的有版本控管的規格。我們在 7 月發布了最新版本。明年 3 月還會有更多內容。第二大支柱是 SDK，因為這是開發者實際用來建置的工具。因此，如果你的 SDK 不安全，那問題就大了。第三大支柱，就是要有一套好的最佳實務，說明如何安全地建置 MCP 伺服器。

01:18 所以，我們今天會簡要討論所有這些內容。大家可能沒注意到的一件事是，當 MCP 最初在 11 月非常早期的規格版本中推出時，

章節 3：早期 MCP 為何把授權交給各開發者（01:23）

01:30 許多授權邏輯基本上是委派給個別開發者處理的。你可以照自己想要的方式各自發揮。你想要 API 金鑰，就有 API 金鑰。你想要憑證，就可以建置憑證。但這麼做有個挑戰，因為如果你開始擴散這種形形色色的實作方式，突然之間，你就有非常廣泛的對象需要去對接建置，而且很難打造出能夠始終如一執行相同操作的用戶端。

02:07 因此，在行動裝置上執行的 LLM 用戶端，和在企業內部執行的 LLM 用戶端，行為就會不一樣，你就得加上一堆自訂的東西，這就很不 MCP，因為如果你還沒發現的話，MCP 本身作為一個協定是非常有主見的，而且是刻意的，因為你希望確保一定程度的一致性。你希望全面推動一致性，包括安全性這類層面。因為如果你一致地這麼做，而且對 auth 該怎麼做有自己的主見——順帶一提，我們全都向 OAuth 看齊，將它作為我們在 MCP 安全性或 MCP 身分驗證與授權所做一切的基礎核心，這讓事情變得容易太多了。

02:47 因為突然之間，你要通訊的所有 MCP 伺服器，無論是你的資料、你的銷售，還是企業內部可能出現的任何人力資源 MCP 伺服器，事情都會再次以相同的方式完成連線。這實際上使我們能夠進行許多創新，你們稍後就會聽到我們與 Okta 等夥伴的合作，我們透過 OAuth 流程建置了許多這類的最佳化，但這一切都取決於 MCP 從一開始就對怎麼做這件事有主見。

章節 4：MCP 為何對安全有主見（03:14）

03:14 不過，有些地方有沒有主見也許其實沒那麼重要。我是說，你可能會爭辯說這很重要，但如果你是在選擇建置應用程式的語言，或是在選擇架在語言之上的框架，你有很多不同的路可以走。那樣沒問題。你建置 Web 應用程式，可能會使用 Vite、可能會使用 React、也可能會使用 Next.js，而且最後很可能都會達到相同的目的地。但在安全性方面情況就不太一樣了，因為如果你把安全性留給不理解安全性的人去處理，你就會走上一些非常糟糕的道路，

03:51 而且因為有人不懂 token 怎麼運作、怎麼儲存、怎麼更新，以及怎麼正確地不把 token 傳到不該傳的地方。因此，當我們從 MCP 的視角來思考安全性時，我們正努力確保大家能被引導至正確的道路上。我認為並非每個人都是資安專家，也不是每個人都想成為資安專家。這也是我從許多與開發者及社群的對話中體認到的一個事實：你有一個問題需要解決。

04:23 你建置 MCP 伺服器是為了做某件事，不管是下訂單還是追蹤包裹。但歸根究底，你真的在乎要從頭開始建置大量身分驗證與授權的東西嗎？大概不在乎。我覺得……我個人在資安領域做很多事，而我也不想處理這些。所以很自然地，隨著規格演進，從 11 月那一版走到 2025 年 3 月—— 以 AI 的時間來算，那感覺已經像是很久以前了——我們向這個概念看齊，並說：「嘿，也許與其把這些選擇權交給大家，

04:55 倒不如讓他們依賴 OAuth 2.1，這是一個以 OAuth 2.0 為基礎的新興標準，再加上一大堆自訂的好東西，讓它稍微更簡單、更安全一點。」當時做的決定大概是：「嗯，你知道 OAuth 需要什麼嗎？你需要一個授權伺服器。而為了讓授權伺服器正確連接到你的 MCP 伺服器，我們會給你一堆事情要做。這包括探索（discovery）、處理登入、單一登入、token 管理，你的授權伺服器和你的 MCP 伺服器會是同一個。」

05:29 這同樣是有問題的，因為回到我剛才跟你們分享的原則：你不會想把安全性的事情委派給不想做安全性工作的人，或是不知道該怎麼做安全性工作的人，因為他們會走上錯誤的道路。

章節 5：讓對的事容易、錯的事困難（05:45）

05:45 那麼，我們要如何確保讓做正確的事變得容易，而讓做錯誤的事變得極度、極度困難？於是 6 月版規格出來了。同樣是去年，我們基本上說：你們知道嗎？與其讓你必須從頭開始實作每一個授權伺服器、處理 token 管理並全部打造出來，不如把這些交給專業人士如何？如果你們是用 Okta 的公司，就用 Okta。如果你是使用 Microsoft 的人，你就會使用 Entra ID。

06:17 這大幅簡化了協定，因為突然之間你就能夠直接隨插即用。如果你想在企業內部新增授權伺服器，而不需要重新實作一套，你可以直接這麼做。這就是我說的：我們想讓開發者非常容易做對的事，並且難以做錯的事。話雖如此，隨著規格演進，我們關注的其中一件事，也是如何確保我們採用那些比我們更理解這些領域的人所制定的標準。

06:49 這就是為什麼我們與 OAuth 社群的夥伴合作，邀請他們參與並提出：「嘿，如果我們想要做授權伺服器探索之類的事，最佳的做法是什麼？」果不其然，對此早已有標準存在。因此，我們依賴這些標準。而 MCP，如果你看看現今的授權規格，它基本上就是建立在無數實際上屬於 OAuth 的 RFC 之上。它們不是 MCP 的東西。沒有人是為了 MCP 去打造這些 OAuth 的東西。你打造 OAuth 的東西是因為那是標準。因此，隨著 MCP 演進、規格改變，在每個版本發布中，我們都在讓大家更容易建置它。

07:25 所以，從 2024 年 11 月我們說「你隨便用什麼、怎麼做都行」，我們變得愈來愈有主見。MCP 是一個有主見的協定，包括授權方面。

章節 6：規模：SDK 與參考伺服器下載達數十億（07:38）

07:38 現在，這是我基本上在每場主題演講之類的場合都喜歡展示的數字。有人想猜猜看這代表什麼嗎？41.7 億。這是我們的 SDK 與參考伺服器自協定推出以來的累積下載次數。41.7 億。我 9 月才剛在阿姆斯特丹。所以，一個多月前，我們才 30 億。我們在一個多月內就獲得了超過 10 億次下載。

08:13 那真的非常多。是的。謝謝大家。向社群致敬。但那真的非常多。有了這個數字，這不一定只是我在投影片上隨便秀出來的虛榮指標，而是它實際上為這項協定提出了一個非常重要的重點：我們肩負著重大的責任。因為在這種規模下，任何失誤、任何資安問題、任何缺口，或是有人把自己的 MCP 伺服器設定錯了，代價都很大。

08:43 所以，協定在 11 月剛推出時，我們從 TypeScript 和 Python 開始，之後就不斷擴張。我們現在有了 Go 的 SDK。還有適用於 Java、Rust 和 C# 的 SDK。你能想到的任何平台，在我們的社群裡都有相對應的 SDK。

章節 7：SDK 安全與協調式漏洞揭露（09:02）

09:02 而如同我提到的，這項協定的安全性不僅取決於我們向 OAuth 靠攏的協定規格，也取決於這些 SDK。因為那才是開發者真正在使用的東西。開發者社群中沒有人會去看規格、讀規格，然後說：「我要從頭打造一切。」他們會下載套件。並且希望該套件運作良好。因此，我們與維護者社群非常非常努力地合作，以確保每一個 SDK 都有走向安全的路徑。我們有標準的揭露流程。

09:32 我們共同合作緩解漏洞。我們共同合作協調漏洞處置。因為認識到 SDK 本身並非獨立存在是很重要的。TypeScript SDK 在 GitHub 上，我上次查的時候，大約有將近 30 萬個公開儲存庫依賴它。30 萬，將近 30 萬個套件、應用程式、儀表板。它可能在本地端執行，可能在遠端執行，也可能在某人的伺服器上執行。

10:04 我們正竭盡所能確保該 SDK 是安全的。Python 也是如此。2.5 萬個套件可不是小數目。那真的非常多。你有 2.5 萬個專案仰賴你把事情做對。這就是為什麼確保我們在資安方面攜手合作，對我們的社群如此重要。這也是為什麼我回到這個想法：我們必須為協調式漏洞揭露之類的事情建立更好的流程，以及如何在它們公開之前修復問題。

10:35 現在，我們談過了 SDK，也談過了規格。

章節 8：安全最佳實務：同意、token 處理與驗證（10:39）

10:39 這其中還有第三個組成要素，那就是資安最佳實務。因為你可以給人們規格，你可以給他們 SDK，但最終你還需要為他們提供指引。你需要為他們提供指引，說明如何確保當他們將 MCP 服務部署到正式環境時，不會做出錯誤的事。所以，在過去的 2 年裡，實際上不到 2 年。我一直提到 2 年，但我知道 MCP 是在 2024 年 11 月修訂的。現在還不是 11 月。我們還不到 2 年。

11:10 但我們看到社群中浮現出許多這類狀況，我們非常非常努力地在各種環境中緩解這些問題，並從社群中吸取經驗。像是引入逐一用戶端同意，因為我們看到當大家將 MCP 服務部署到正式環境時，他們會遇到混淆代理人（confused deputy）的情境，同意了不該同意的東西，而且大家都知道，隨著許多模型能力愈來愈強，你不會想留下任何途徑，讓這當中很多事情被自動化。像 token 直通轉傳（token pass-through）這類的事情。再次強調，必須意識到該如何處理 token，考慮到這點非常非常重要。

11:43 如果你的 MCP 伺服器就是拿到 token 的那一方，你不會想把這個 token 再傳到別的地方。所以，我們引入了像受眾驗證這類的機制。同樣地——順帶一提，不只是受眾，還有簽發者驗證（issuer validation），用來確保不會發生混淆攻擊（mix-up attack），這是在最近一版規格中推出的。這些大多源自於我們觀察大家如何在正式環境部署 MCP。

章節 9：實際部署的教訓（12:03）

12:04 這一切都立足於真實世界的實際部署、真實世界的使用情境，以及我們從社群獲得的回饋。所以，如果你正在正式環境部署 MCP 伺服器，請讓我們知道哪些行得通、哪些行不通，特別是在資安方面。所以，這也……我談到的許多最佳實務和環節，都已經融入我們的流程中。當我們設計新的規格內容、設計新的 SEP，也就是規格增強提案（spec enhancement proposals）時，我們現在不只是丟出像是：「嘿，

12:36 這裡有些文字讓你們去閱讀並評估是否……像是，我現在正與我們的社群一起進行的其中一件事就是檔案上傳。檔案上傳這件事，如果你真的仔細看，可能是很有風險的操作，因為你突然間就多了一個內容外洩的管道。因此，為此我們必須確保從一開始就徹底考慮資安問題。這是基礎的一環。資安是不可妥協的。這不是事後才考慮的事。不是我們隨規格發布了某個東西，規格發布後才說：「啊，資安。」

13:07 它實際上已經融入到我們的流程中。

章節 10：一致性測試：SDK 的契約（13:10）

13:10 我們現在也藉助一致性測試，把許多這類事情自動化，因為一致性測試讓我們能確保所有 SDK 都做對的事。所以，當我說我們現在有這麼多不同的 SDK 時，重要的是不必靠任何人手動去確認設定是否正確。一致性至關重要。所以，現在當我們有任何提交給某個 SDK 的問題時，例如有人針對 Python 回報了某些問題，我們會在我們擁有的其他 SDK 的整個生態系中協調此事，以確保同一個問題能盡快得到評估並以最快速度做出反應。

13:47 再次強調，這是整個生態系的事，我們不只專注在單一個 SDK。我們現在也針對像 SDK 一致性之類的事情建立了要求。我一直說一致性算是基礎的一環，但基本上它是一份契約，確保如果有回報資安問題且有影響客戶的重大錯誤時，有明確的預期標準。如果你是 Tier 1（第一等級）的 SDK——順帶一提，我們已經建立了一套等級（tier），規範 SDK 怎麼發布和更新，讓你們

14:17 採用者、企業、新創、教育、醫療等各行各業，對如何處理這些 SDK 問題抱有預期。對於資安非常重要。在我們目前大約 116 個一致性情境中，超過三分之一——應該說接近三分之一，沒有超過——實際上是以資安為導向的。授權、授權相關的事務、授權周邊的事項都融入其中，以便當新的 SDK 推出時，

14:48 當 SDK 流程引入新的 SEP 時，同樣地，資安都已內建其中。它不是事後才考慮的事。你不會在發布之後才去考慮資安。這點很重要，因為如果我們沒有這種契約，它基本上就只是一項建議。而我們知道建議通常會被忽略。因為你可能無論……你大可以說你絕對應該這麼做，但如果沒有自動化、沒有強制執行的流程，你就永遠無法依賴它。

15:19 所以這就是為什麼我們非常非常推崇契約，在這種情況下就是 SDK 的一致性測試套件。所以回到我們讓事情更安全的地圖，過去一年半以來我們一直在建立這些。現在 OAuth 2.1 的整套內容都有妥善的支援。我們有良好的資安文件。我們有良好的漏洞回報機制。我們在各 SDK 之間協調。我們有一致性。但還有什麼？

15:49 我們其實還沒完成。

章節 11：面對 agent，同意機制為何得改變（15:52）

15:52 我們還沒完成，是因為自從 MCP、第一版 MCP 規格發布以來，世界已經改變了。當 MCP 處於起步階段時，大致的假設是電腦前會有一個人去點擊按鈕。你會有人同意登入提示。你需要存取你的 Gmail 帳號。他們會點擊核准。那樣沒問題。那樣運作得相當好。但這已經不太能擴展了。因為突然之間，正如各位今天早上在稍早 David Sarratt 那場主題演講中看到的，

16:30 模型開始運作的範疇變得廣大得多。而這在實務上意味著，不會再有一個人去點擊那個按鈕來同意某件事。而這在實務上意味著，你需要一種更好的方式來同意各項事務，無論是存取你的 Gmail 帳號，還是對你的銷售資料進行操作。也許它需要排程某件事，或是從雲端某處的某個資料儲存區拉資料。所以，為此我們思考了到底缺少了什麼？而針對這些，這裡有 4 個關鍵組件。

章節 12：企業託管授權（17:00）

17:05 其中一個是我們今年稍早推出的，也就是企業託管授權（enterprise-managed authorization）。我們與 Okta 的夥伴進行了合作。這基本上讓任何想連線到 MCP 的使用者——順帶一提，這項功能今天已經在 Claude 上線—— 你只要連線你的 MCP 伺服器一次（你的管理者會處理這件事），之後組織中的任何人都永遠不會看到同意提示。超級強大。你永遠不必擔心有人不小心連線了自己的個人 Gmail 帳號，並讓他們的 AI 用戶端把東西傳進那個收件匣。

17:40 我們也正在做更多擴充，例如 DPoP（demonstrating proof of possession，持有證明）、工作負載身分聯邦（workload identity federation），以及其中我其實最興奮的一個，叫做 WAG，也就是 workload authorization grant（工作負載授權授予），由我們的同事 Paul Carleton 在推動。前面我談到了企業託管授權，也就是 EMA。你可能會聽到不同的稱呼方式。可能是 EMA、ID-JAG、XAA，但它正是我剛才所描述的。你有一個像 Okta 這樣的企業 IDP，基本上會聯邦化許多連線，然後你的使用者就不需要登入超過一次。

18:13 順帶一提，我在這張圖上寫的是員工，但這其實同樣適用於 agent。各個 agent 也會做同樣的事。

章節 13：DPoP：把 token 綁定到裝置（18:21）

18:21 另一個是 DPoP，也就是持有證明（demonstrating proof of possession），這點至關重要，因為正如各位從持有者 token 的概念中所知，token 本質上是與持有者關聯的。由某個人持有它。問題在於，如果你有許多服務，到處都漂浮著這些 token，有人就能輕易將其竊取外洩。如果有人拿到了可存取你 Gmail 收件匣或財務資料的 token，那可就是個問題了。DPoP 實際上是透過一些輕量密碼學來幫你綁定 token。

18:55 我先大致帶過細節就好。讓 token 綁定到裝置上。所以如果你的裝置有信賴平台模組（TPM）晶片，就會用它來產生私密金鑰、簽署 token，接著即使攻擊者稍後拿到了該 token，也無法使用。這對 MCP 來說非常重要，因為 MCP 可以在任何環境中執行。

章節 14：工作負載身分聯邦（19:16）

19:18 工作負載身分聯邦很有意思，因為隨著 MCP 被部署在眾多不同的服務機群中，你可能在 GCP 的 Kubernetes 叢集中執行，也可能在 Azure 或 AWS 中執行。你通常如何給予那些伺服器、MCP 伺服器或基礎架構憑證？是 API 金鑰，也可能是像用戶端 ID 與用戶端密鑰這類用來執行操作的用戶端憑證。可能在某個地方有一個 HashiCorp Vault 來儲存這些憑證，並期望它是安全的。然後有一天有人攻破了 Vault，接著你所有的金鑰都被竊取外洩了。

19:53 這同樣也是個問題。所以，工作負載身分聯邦基本上讓你可以說，你的雲端供應商、你的平台，也就是你的服務不管在哪裡執行的底層基礎，都會提供該平台的身分，供你的服務使用——也就是讓身為 MCP 伺服器的工作負載來識別自身，接著使用那些短期憑證。這裡的關鍵是短期有效。即使有人攔截了它，能使用的時間也非常有限。接著再用它為下游服務產生其他 token。

章節 15：工作負載授權授予與 agent 身分（20:25）

20:25 我前面提到工作負載授權授予（WAG）算是這裡比較重要的部分之一，而它其實也是我們現在認為通往 agent 身分的那條路。我們已經在 Claude Tag 中採用了它。Claude Tag 是我們在 Slack 裡面執行的 agent。它允許 agent 向下游服務識別自身身分，無論是 SaaS 服務還是你自己的基礎架構。所以，如果在過去你有一個需要執行某些操作的 agent 平台，你會如何給它憑證？

20:55 大概會有人以自己的身分登入並說：「噢對，沒問題。我是 Den，拿我的 token 去做事吧。」或者他們同樣會使用靜態憑證。那樣無法擴展。在 agent 領域肯定行不通，因為你現在有 agent 在許多不同的環境中執行這麼多的任務。在這種情況下，WAG 正在建構——它在某種程度上呼應了 WIF 與 ID-JAG 的許多概念。實際上它也建立在 OAuth 的許多概念之上。還記得我說過我們試著不重新發明輪子，並確保 MCP 使用 OAuth 標準嗎？

21:27 就是這個了。WAG 將會成為一個給予 agent 專屬身分的真正 OAuth 標準。不只如此，他們還會把一些東西內建到 agent 裡，讓你能針對 agent 做什麼來做政策決策。所以 Claude Tag——是我的團隊在打造的——實際上就是用這個來識別 agent，並嵌入宣告（claims），內容包括你的 Slack 工作區、頻道。這樣一來，如果你接收到一個 agent，你就會知道該 agent 是在哪裡操作或正嘗試做什麼。

21:57 這表示你會為該 agent 取得一個短期 token，然後你的服務就能在此基礎上做出授權決策，完全清楚該 agent 是什麼。
